# 3.1 No Code / Low Code 概念

## 3.1.1 定義

**AI 民主化：** 用視覺化降低門檻，讓非工程背景也能參與做 AI 應用。

| | No Code | Low Code |
|--|---------|----------|
| 怎麼做 | 拖放、範本、幾乎不寫程式 | 視覺化為主，少量程式補足 |
| 適合誰 | 業務、快速原型、小型內部工具 | 有技術背景、中大型、要客製與整合 |
| 彈性 | 低 | 較高 |
| 風險 | 天花板、廠商鎖定、稽核不透明 | 仍有鎖定，但較能接 API |

TensorFlow／Keras 等也有視覺化介面，讓無程式經驗者能組 ML 流程——考的是「降低門檻」，不是叫你背操作步驟。

生成式 AI（ChatGPT、DALL-E）疊在 No/Low Code 上，常見能力：自動生程式、優化模板、數據分析建議、依文字生 UI、行銷文案、個人化 App 快速組裝。

**易混：** Copilot／Cursor 幫你寫 code ≠ 整個專案變成 No Code。能做出 Demo ≠ 能上生產（權限、log、備援、資料落地）。

## 3.1.2 產業場景（記「痛點→生成式能做什麼」）

| 產業 | 生成式＋No/Low Code 常出現的用法 |
|------|----------------------------------|
| 醫療 | 分子結構預測輔助新藥、個人化療程草案、病歷整理與輔助診斷（醫師仍決策） |
| 製造 | 設計方案生成、製程改善建議、原型加速 |
| 金融 | 情境模擬做風險、投資組合建議、合規監控輔助 |
| 零售 | 個人化行銷文案、庫存預測、推薦 |
| 教育 | 教材生成、個人化學習路徑、自動評量回饋 |
| 客服 | 虛擬客服、自動回覆草稿、客訴趨勢分析 |

改善客戶體驗的技術方案，選項出現 **NLP＋生成式回應** 通常比「預測性維護」更直接。

## 3.1.3 選平台的六大評估（必背標題）

1. **目標用戶與技術需求：** 純業務拖放 → No Code；要複雜邏輯與企業整合 → Low Code。
2. **功能與擴展性：** 能否接 CRM／ERP、自訂報表與工作流。
3. **安全性與合規：** 加密、身分驗證、細緻權限。個資法／GDPR／CCPA 對得上。
4. **成本與效益：** **TCO**（購買、維護、培訓、隱性費用）與 **ROI**（縮短上市、效率）。只比授權單價是錯的。
5. **技術支援與社群：** 文件、客服、論壇活不活。
6. **市場評價與案例：** 同業成功案例，不要只看官網文案。

## 3.1.4 結合生成式的挑戰與解方

| 挑戰 | 典型症狀 | 解方方向 |
|------|----------|----------|
| 準確與可靠 | 幻覺、錯內容進生產 | 多層驗證：自動檢測＋**人工審核** |
| 隱私與安全 | 敏感資料進公有模型 | 加密、匿名、權限；禁止亂貼客戶名單 |
| 倫理 | 假訊息、訓練偏見 | 使用規範、公平性檢測 |
| 整合與效能 | API 接不穩、GPU 不夠 | 開放 API 的平台、雲端分散負載 |

四個穩健面向：數據品質（多樣、定期更新）→ 模型多維評估（準確／可靠／創造性、壓力測試）→ **人機協作**（關鍵場景人工干預）→ 資安（防攻擊、弱點掃描）。

## 3.1.5 市場價值（選「效益敘述」用）

- 降低開發成本：少請一堆工程師做重複內部工具；業務能參與。
- 縮短上市：現成模組、API、敏捷改功能。
- 可擴展與訂價彈性：流量與功能成長時能調。

企業導入 AI 後**最直接**的影響，練習題方向是提升生產力與效率，不是「增加人力需求」或「降低競爭力」。

## 3.1.6 何時用、何時不用

| 較適合 | 較不適合 |
|--------|----------|
| 內部試作、表單、簡單自動化、兩週驗證值不值得做 | 核心交易、高風險核決、嚴格低延遲 |
| 標準連接器就夠 | 深度客製協定、要可移植避單一雲死鎖 |
| 業務先跑通流程 | 稽核與問責要求極高卻完全黑箱 |

**治理不會因為 No Code 而消失。** 個資、權限、測試、問責一樣要做。

員工提升 AI 能力：跨部門交流＋測試專案，比「自己看心情自學」有效。教師帶學生用生成式：訂使用規範並說明，不是全面禁止或無限制。

# 3.2 生成式 AI 應用領域與工具使用

## 3.2.1 生成式是什麼

核心：學資料分布後**生成新內容**，不是只分析既有資料。常見骨架：GAN、VAE、Transformer。ChatGPT 2022-11 後把人機互動與產業應用推到前線。

技術架構三塊：

1. **深度學習網路：** 多層特徵；**自注意力**處理長距離依賴。
2. **訓練資料處理：** 清洗、**Tokenization**（切詞／子詞）、向量化。
3. **推理採樣（必考）：**

| 參數 | 作用 | 實務 |
|------|------|------|
| Temperature | 隨機性 | 低＝保守穩定（FAQ、合約草稿要準）；高＝較有創意（發想，仍要人審） |
| Top-k | 只從機率最高的 k 個 token 抽 | 限制胡亂字 |
| Nucleus（Top-p） | 從累積機率達閾值（如 0.9）的集合抽 | 比固定 k 更彈性 |

生成式特點：上下文理解、遷移學習、多模態、prompt 可控。挑戰：算力、幻覺、偏見、安全。演進：壓縮量化加速、模組化、領域微調、多模態融合。

## 3.2.2 市場與社會影響

- 規模成長、創業投資、訂閱與客製方案、永續（能耗）。
- 就業雙面：重複性工作被取代；新興職如提示工程師、AI 訓練師。
- 效益：直接（降本增效）、間接（新商業模式）、衍生（雲與硬體）。
- 迫切挑戰：資料隱私與倫理規範（指引練習方向），不是「算力過剩」。

生圖要同時考慮：解析度、**版權合法性**、推論時間——「以上皆是」。使用生成內容要標注來源、人工審查，不是直接當學術報告。

## 3.2.3 技術突破與工具趨勢（記方向不背價目）

突破：GAN 高品質圖；VAE／Flow 較穩的機率生成；Transformer＋Self-Attention（GPT、DALL-E、Stable Diffusion）；預訓練＋微調＋**RLHF**（人類回饋強化學習讓輸出更貼人）；推理加速（如 vLLM）、邊緣部署。

發展方向：

- 模型變大（LLM）＋多模態（文生圖 Midjourney、DALL-E）。
- 輕量化：壓縮、量化、個人化客製。
- GAN 與擴散融合提升真實感。
- 開源生態：Hugging Face 等加速整合。
- 垂直產業：法律文件、醫療報告、金融風控、教材。
- **AIaaS：** 不用自備高階硬體，用 OpenAI API、Hugging Face Spaces。
- 可控性：微調＋提示工程＋風格參數。
- 協作與即時迭代。
- 安全：本地部署、加密、版權過濾。
- 道德法規：深偽、假新聞、標示 AI 生成。

工具怎麼選（評鑑與考題曾出現的用途，品牌會變，記用途）：

| 需求 | 方向 |
|------|------|
| 對話、草稿 | 對話型 LLM |
| 系統整合、控 token | API |
| 多模態理解 | 多模態模型 |
| 寫程式 | Copilot、Cursor 類 |
| 流程／代理工作室 | Copilot Studio 等 Low-Code 代理 |
| 生圖 | Midjourney、DALL-E、SD 類 |
| 語音轉文字 | Whisper 類 |

選項出現「要引用內部知識」→ **RAG 或有來源的檢索**，不是只調 temperature。

## 3.2.4 提示工程

| 技法 | 何時用 |
|------|--------|
| Zero-shot | 簡單、模型已會 |
| Few-shot | 要固定格式、口吻、欄位 |
| CoT 思維鏈 | 要逐步推理 |
| ToT 思維樹 | 多分枝探索；成本高，簡單題不值得 |
| 角色／約束 | 限定專家角色、禁止事項、輸出 schema |

Prompt 寫更長**救不了**知識不在上下文裡。知識會變 → RAG。行為／口吻要長期改變 → 才評估微調。

## 3.2.5 RAG vs 微調 vs Agent（公告題核心）

**RAG（Retrieval-Augmented Generation）：** 先檢索再生成。解決知識過時與胡謅，讓答案可追溯到片段。

答得不準時檢查順序：

1. 資料有沒有、權限對不對  
2. Chunking 切太碎／太長／切錯邊界  
3. 檢索（關鍵字／向量／混合）  
4. 才換更大模型  

有搜尋框但沒把檢索片段餵給生成，不算完整 RAG。

**微調 Fine-tuning：** 用領域資料改模型權重。適合穩定的格式、口吻、任務行為。成本高、資料要更新就再練。SOP 每月改 → **優先 RAG**，不是從零訓練或動不動全量微調。

**PEFT／LoRA：** 參數高效微調，只訓少量適配參數，省算力與儲存。考「不想動全模型又要領域化」時選它。不是另一種 RAG。

**Agent：** 感知 → 規劃 → 行動（呼叫工具／API）。要多步、查庫、開單、跨系統才需要。規則清楚的單次問答不必上 Agent。多代理要防互等卡死：逾時、heartbeat、failover，不是把 prompt 寫更長。

**MCP（Model Context Protocol）：** 模型連外部工具／資料的協定思路——「怎麼接工具」，不是另一個 LLM 品牌，也不是 RAG 的替身。

選型口訣：

```
知識要新、要引用     → RAG
口吻／格式要長期像我們 → 微調（可 PEFT）
要動手呼叫系統       → Agent（＋工具／MCP）
只要穩穩答一句       → 單次 LLM＋低 temperature
```

## 3.2.6 應用領域（規劃題用「輔助不是取代」）

- 藝術設計：靈感與細節輔助，創作者仍負責構思；注意版權。
- 醫療生技：分子、合成影像、個人化建議、醫學教育模擬；診斷責任在醫師。
- 教育：個人化內容、助教、VR 教材；要使用規範。
- 娛樂媒體：地圖／劇本／虛擬主播；深偽風險。
- 產品製造：草圖、3D 原型、模擬報告、供應鏈預測。

生成式基礎技術選項裡，**GAN** 常是正確項（相對決策樹、聚類、隨機森林）。

# 3.3 生成式 AI 導入評估規劃

導入順序（寫得出來就能拿規劃題）：

**問題與目標 → 資料能不能用 → 方案選擇 → 成本效益（TCO／ROI）→ 試點測試 → 權限與監控 → 擴大。先選模型品牌是錯序。**

對照文件方向：經濟部產業發展署《AI 導入指引》、公部門手冊、金管會金融業 AI 指引（看場景選）。

## 3.3.1 評估標準（五塊，第 3 塊標題已勘誤）

**（1）需求與現狀**

痛點、場景（品質、週期、體驗、供應鏈）、技術是否真能解核心問題。規則引擎就夠就不要硬上生成式。

**（2）資源與基礎設施**（這一點才是資源）

人才、數據完整性與清洗、硬體／雲與資安、架構可擴展。資料品質差，再貴的模型也歪。

**（3）企業導入階段性實施策略（勘誤）**

原文標題誤為「資源與基礎設施評估」（與第 2 點重複）。勘誤後本點是**分階段**：

- 試點：小範圍、可驗證、風險可控  
- 階段擴大：依試點結果推廣  
- 長期目標：納入企業策略  
- 持續優化與回饋  

不要把第（2）（3）點搞混。

**（4）員工技能與文化**

分職能培訓、實務操作、鼓勵跨部門，而不是只買授權。

**（5）風險評估與管理**

資料安全隱私、倫理法規、模型偏誤與失效應變、資金人力調度。

優先級：先做**低難度、快見效、不拖垮其他業務**的場景；資源需求高且短期難見效的延後。

三階段願景：

| 階段 | 重點 |
|------|------|
| 初始／試點 | 驗證真實場景、收回饋、累積經驗 |
| 成長／推廣 | 跨部門、從單點到多環節（內容→分析→客服→供應鏈） |
| 成熟／創新 | 系統化營運、差異化、滾動對齊戰略 |

人才：內部課（LLM、微調、資料、怎麼選模型）＋外部專家／廠商縮短學習曲線。

## 3.3.2 規劃落地（準備 → 設計 → 營運）

**準備：挑選方案**

- 用營運數據、員工與客戶回饋找問題；先簡單可行（內部檢索、客服草稿）。
- 畫流程、找重複規則化工作當候選。
- 檢視資料是否夠、算力／儲存、人力技能；不夠就升級、外援或訓練。
- 方案：商業產品／開源／客製；看功能、適配、擴展、**成本結構（授權＋硬體＋營運＋隱性）**、支援評價。
- 優先順序：商業價值、技術成熟、資源、是否符合長期戰略。

**設計：確認規格**

- 可量化 KPI（初判正確率、處理時間、錯誤率）。
- POC：小規模看準確率、效率、能否融入現況、員工會不會用。
- 算 ROI 與回收週期；有效再擴大。

**營運**

人員會用、持續監控、效能掉或環境變就微調或重訓。資料漂移要能被發現；最好有重訓管道，達警戒值觸發更新。價值擴散：內部分享、培訓、獎勵，從單點到全公司。

## 3.3.3 風險管理（科目二最高頻）

三大塊：倫理與偏見、資料安全隱私、合規與智財。

| 風險 | 規劃師動作 |
|------|------------|
| 個資／機密進公有模型 | 禁傳、私有化、最小化、契約與 log |
| 訓練資料被模型背出來 | 去識別、差分隱私、存取控制 |
| 提示攻擊／注入 | Guardrail、權限分離、秘密不放進 prompt |
| 對抗性輸入 | 監控、過濾、紅隊 |
| 幻覺當官方回覆 | RAG、引用、低 temperature、人工放行 |
| 偏見歧視 | 多樣資料、公平測試、申訴與覆核 |
| 智財／深偽 | 訓練與輸出授權、標示 AI 生成、內容過濾 |
| 高風險場景問責 | RACI：誰能上線、誰覆核、誰能關機；醫療金融責任不能丟給模型 |
| 反向工程推訓練資料 | 限流、監控異常查詢 |

高風險項目優先緩解：加強審核、偏見檢測、透明標示「此內容由 AI 生成」。定期審核＋員工風險意識訓練。

TCO 提醒：便宜模型省 token，可能增加覆核人力，總成本未必低。試點成功 ≠ 全面上線（權限、備援、營運人力沒跟上）。

## 3.3.4 科目二解題習慣

1. 這題該不該用 AI？規則是否就夠？
2. 鑑別／生成／RAG／Agent／Low-Code 哪個**夠用就好**？
3. 資料能不能出域？誰覆核？
4. 「最不適當」常是：全公司一個公有 GPT 不加分級、試點沒過就全面、只比 API 單價、無限制讓學生用 AI 交作業、生成內容不標來源、導入先選最潮模型。

## 科目二閉卷清單

- No Code vs Low Code 各一句；六大評估能默寫標題。
- TCO 含哪些成本。
- Temperature／Top-k／Nucleus 各管什麼。
- RAG vs 微調 vs Agent vs LoRA vs MCP。
- 導入五評估＋勘誤後第（3）點標題。
- 試點 → 擴大 → 成熟。
- 個資、幻覺、提示攻擊、問責各一個控制措施。

# 補篇 A｜工具與架構（公告題比指引細）

## A.1 RAG 實務坑

長文件整份丟進檢索 → 噪音大、找不到關鍵句。要 **chunking**（按標題、段落、重疊窗口切）。切太碎失去脈絡，切太長檢索變鈍。

法規常更新：優先更新索引與文件版本，不是每次全量微調。檢索不到新函釋，再大的模型也會講舊法。

高流量 RAG：快取常見問、非同步建索引、混合檢索（關鍵字＋向量）。延遲高時先查檢索與 rerank，不要先換 10 倍參數的模型。

表格／Excel：模型吃「原始格子」常亂。先轉成清楚的文字或 markdown 表、標欄位名，再送 LLM。

## A.2 MCP vs RAG vs Agent

| | 解決什麼 | 不是什麼 |
|--|----------|----------|
| RAG | 把外部知識片段塞進生成上下文 | 不是自動去呼叫任意 API 辦事 |
| MCP | 模型如何**標準化接上**工具與資料源 | 不是另一家 LLM、也不是檢索演算法 |
| Agent | 多步規劃、選工具、看結果再行動 | 不是把 prompt 寫長就會規劃 |

情境感知 Agent：依當前對話／環境狀態選下一步，**不是**每次重訓模型。  
Solution Graph：把複雜任務拆成節點（步驟／工具）與邊（依賴），方便規劃與失敗重試。

多 Agent 互等：加超時、重試上限、人工接管，不是加更長系統提示。

## A.3 微調與 PEFT

企業專屬知識要寫進權重，但 GPU 很小 → **LoRA／QLoRA／Adapter** 等 PEFT，不是先買一排 A100 再全量微調。  
內部 SOP 月月改 → RAG 為主。  
要固定「我們公司的回覆口吻與欄位」→ 微調或強 prompt＋few-shot。  
新市場資料跟 few-shot 差很多 → 補該市場例子或檢索該市場知識，不是把 temperature 調到 1.5。

RLHF：用人類偏好排比來對齊輸出，適合「已會說話但不合規範」。

## A.4 生成品質與出處

同一偏好設定下不同族群推薦差異過大 → 查資料偏見與公平，不是只加更多生成多樣性。

客服「整體 QPS 很高但仍卡頓」→ 可能是解碼延遲、排隊、未串流（streaming）；吞吐高 ≠ 單筆延遲低。

影片／圖像出處證明（provenance）：浮水印、內容憑證、元資料。考「何者不屬於官方機制」時，把「完全無法被偽造所以不用審」這類絕對句當錯的。

GPT-Realtime 類：適合語音／低延遲互動，不適合大型離線批報表。

程式輔助工具：在編輯器裡依上下文建議程式碼，仍要人審與測試；不是自動擁有著作權或保證無漏洞。

Vibe coding／MVP：快，但缺測試、權限、可維護性時，不能直接當生產。

## A.5 Low-Code 進階判斷

儀表板要「分析可信」→ 權限列級、資料來源可追溯、計算邏輯不可被亂改，不是只選最漂亮的圖。

部門自建應用擴大後：統一身分、稽核 log、資料分類、防止影子 IT 把名單貼到公有模型。

邊緣運算＋No/Low Code：設備端要考慮斷線、模型套件大小、延遲；不是所有邏輯都回雲端。

門市主管自己改看板 vs 行銷建預測模型：前者 No Code BI；後者常要資料科學／AutoML／Low Code ML，深度不同。

## A.6 導入補充

資料漂移：上線後輸入分佈變了，監控特徵與輸出，達門檻重訓。  
自動化重訓管道：警戒值觸發，減少人工作業時間，但仍要驗證才能上生產。

高風險（授信、醫療生成建議）：人審、可解釋、申訴、不能把責任寫成「AI 說的」。

生成內容當對外官方：引用、標示 AI、法務看智財。

# 補篇 B｜指引風格自測

1. 生圖要考慮：解析度、版權、推論時間（常為以上皆是）。  
2. 教師帶學生：訂規範並說明，不是禁或放任。  
3. 改善客戶體驗：NLP＋生成式回應。  
4. 員工能力：跨部門交流與測試專案。  
5. 導入後最直接影響：生產力與效率。  
6. 生成式基礎技術之一：GAN。  
7. 迫切挑戰：隱私與倫理。  
8. 生成內容品質：標來源、要人審。  
9. 使用體驗優化**不是**「限制使用者自訂」。  

導入題自己用話講一遍：需求 → 資源基礎設施 → **階段性實施（試點擴大）** → 文化人才 → 風險。第 3 點標題不要寫成資源評估。

# 補篇 C｜科目二判斷卡

**選方法**

- 內部知識要可引用、常更新 → RAG。  
- GPU 不夠還要領域化 → PEFT／LoRA。  
- 要查庫、開單、跨系統 → Agent。  
- 只要穩答 FAQ → 低 temperature＋RAG，不必 Agent。  
- MCP 是接工具的協定；RAG 是塞知識。

**風險紅線**

- 客戶名單進公有 ChatGPT → 擋。  
- 無人工的自動拒貸／自動診斷結論 → 擋。  
- Low-Code 上了核心計費 → 鎖定、稽核、正確性風險。  
- 只比 token 單價 → 忽略覆核 TCO。  
- 試點沒過就全公司一個 GPT → 錯序。

**提示**

- 要穩定：降 temperature、加格式範例。  
- 要推理：CoT。  
- 要探索方案：ToT，貴。  
- 知識不在上下文：檢索，不是把 prompt 再寫兩倍。

**樂雲場景對答案**

- 業務要自己做 GPT 客服：Low-Code 可試點；客戶資料、提示外洩、升級路徑先畫紅線。  
- SOP 月更：RAG。  
- 方案建議書草稿：生成；雲端用量是否異常：鑑別。  
- 全公司一個 GPT：先分級（公開網／內部 RAG／禁止上傳）再談工具名。
